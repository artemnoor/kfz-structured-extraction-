- Сохранённый предыдущий benchmark указывает 22 результата Rules Only. В текущем checkout доступны только 6 Parser JSON, все помечены демонстрационными; прежний прогон остаётся историческим снимком и не воспроизводится из текущих файлов.
- Пять исходных документов независимо сверены с содержимым, а не с именами: скан PDF КФЗ, XLSX ведомость, скан PDF акта, PDF со слоем текста и DOCX записка.
- На этих пяти документах тип совпал в 5/5. Из них один скан корректно оставлен в статусе `review` из-за пониженной уверенности.
- Независимые проверки полей: 14/14. Проверки нормализации значений: 25/25. Это ручная выборка, не метрика точности всего корпуса.

Для этих оригиналов в текущем checkout нет сопоставленных Parser JSON и результатов извлечения, поэтому расширенная accuracy не рассчитана.
- Полные precision/recall/F1 классификации, реквизитов и строк корпуса имеют статус `not_scored`: для большинства оригиналов нет независимых пар «исходный документ — результат Parser — результат Structured Extraction».

## Ошибка и исправления

Независимая проверка скана акта обнаружила, что короткая метка «Заказчик» по подстрочному совпадению попадала также в поля «Представитель заказчика» и «Замечания заказчика». Теперь короткая метка не заполняет более конкретное поле. Добавлена регрессия, проверяющая, что эти поля остаются `null`/`missing` без отдельного исходного свидетельства.

Дополнительно Rules Only извлекает номер из типизированного заголовка акта, счёта-акта и записки; key-value таблицы и XLSX ячейки используются с их исходными локаторами; период вида «Январь 2026» нормализуется в полные границы календарного месяца. Для счёт-акта дополнительно исправлен поиск даты в паре «метка/значение», попавшей в Parser-заголовок таблицы.

Добавлены регрессии на все 15 финансовых колонок КФЗ, многоуровневые заголовки, физический индекс ячейки, единицы измерения и точный provenance. Конфликтующие поля остаются в `review` с `value: null`; отсутствующие — `null`. Формулы без надёжного результата не пересчитываются автоматически.

## Синтетические тесты и стабильность

- `npm test`: 48/48. Добавлен тест: формула XLSX без cached value остаётся `review`/`null` и сохраняет адрес `C8`.
- `npm run test:api`: PASS; проверены локальная D1, повторное Rules Only извлечение, история и отказ на анонимной записи. Smoke использует фиксированный ID тестового документа; два последовательных запуска не увеличили число документов. Из локальной D1 удалены только 13 старых UUID-записей API smoke.
- Повторный Rules Only прогон по шести Parser JSON, реально имеющимся в checkout, завершился без исключений; все шесть входов демонстрационные. Это не метрика точности на оригинальном корпусе.
- В локальных 11 исходных XLSX обнаружены 5 формульных ячеек без cached values (по одной на файл, адрес `C8`). Для этих пяти оригиналов результат извлечения отсутствует; соответствующий `review`/`null` сценарий проверяется регрессией на Parser JSON фикстуре.
- Для четырёх сканированных PDF страниц выполнена визуальная проверка. На скане КФЗ локальный OCR-пробник 4× с PSM 11/12 распознал 5/5 кодов статей и единицу человеко-месяцев, но не выделил строку 2026 года отдельно. Это диагностика Tesseract, не OCR Document Parser; метрика его OCR на этой паре не пересчитана.
- Существующие регрессии проверяют явный LLM allowlist, сохранение provenance при повторном извлечении, отсутствие дублирования Parser-фрагментов и идемпотентное заполнение демонстрационных записей.
- Документы корпуса в Polza не отправлялись. Секрет хранится локально в игнорируемом `.dev.vars`; отчёт и benchmark не содержат ключа, исходных Parser JSON, исходных имён или финансовых значений.

## Polza AI

Модель текущей конфигурации и повторного теста: `google/gemma-4-26b-a4b-it`. `GET /models` использовался только для проверки каталога; inference подтверждён отдельными completions.

После штатного сброса дневной квоты `npm run test:polza` завершился успешно на синтетическом демо-документе:

| Режим | Модель | Время | Prompt tokens | Completion tokens | Всего |
|---|---|---:|---:|---:|---:|
| LLM Assisted | `google/gemma-4-26b-a4b-it` | 9 481 ms | 12 739 | 857 | 13 596 |
| Compare | `google/gemma-4-26b-a4b-it` | 20 963 ms | 12 740 | 1 170 | 13 910 |

Оба ответа прошли локальную JSON-схему и source grounding; результат каждого режима сохранён и прочитан из D1. Compare: 27 совпадений, 2 расхождения, 0 значений только Rules Only и 0 только LLM. Расхождения не принимаются автоматически. UI показывает невыбранное LLM значение отдельно от значения Rules на проверке и ведёт к подсвеченной ячейке источника.

В локальной D1 сохранены и повторно прочитаны 10 успешных Gemma completions: 5 `llm_assisted` и 5 `compare`. Последний полный smoke на этой ветке: Assisted — 13 345 ms, 12 740 prompt + 1 393 completion = 14 133 токена; Compare — 2 781 ms, 12 740 prompt + 863 completion = 13 603 токена. Все 10 записей имеют модель Gemma, usage и `response_validated=true`. История включает HTTP 429 `AI_DAILY_LIMIT` до провайдера (0 inference) и исправленный smoke assertion: D1 history возвращает `id`, не `extraction_id`. Защита не обходилась.

В Polza отправлялся только синтетический документ; документы корпуса не отправлялись. Провайдерские usage и latency записаны в выводе smoke, но стоимость не включена в benchmark.

## Браузерная проверка и вердикт

Playwright локально проверил выбор КФЗ, запуск Rules Only, LLM Assisted и Compare, отображение результата и конфликтов, переход к provenance и подсветку исходной ячейки. Проверен также выбор другого демо-документа и Rules Only. Production deployment не выполнялся.

### Вердикт: `READY_WITH_LIMITATIONS`

К Document Linking можно переходить для пилотного контура при сохранении ручной проверки всех `review` значений: семантическая регрессия КФЗ 15/15, API/Worker/D1 проверки, 10 реальных Gemma completions, allowlist и браузерный provenance прошли. Это не подтверждает production-качество полного корпуса. Перед снятием ограничений нужно сохранить и сопоставить свежие Parser JSON с оригиналами для разных форматов, оценить классификацию/поля/строки на независимой разметке и сверить фактический OCR Document Parser на сканах, включая строку КФЗ 2026. Неоднозначные и формульные значения остаются на ручной проверке.
